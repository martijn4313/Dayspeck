### **Project Overview**
This memo outlines the finalized technical architecture and UI/UX strategy for the ESP8266-based Motorcycle Weather Display. The goal is to provide a highly responsive, real-time weather tool for riders, bypassing the single-core CPU and memory limitations of the ESP8266 through aggressive data filtering, lightweight storage, and non-blocking UI techniques.

---

### **1. Core Architecture & Networking**
To prevent animation freezing and out-of-memory crashes on the ESP8266, the data-fetching pipeline must follow the **Filter $\rightarrow$ Stream $\rightarrow$ Struct** methodology.

*   **Protocol Optimization:** Use **HTTP instead of HTTPS** for the Open-Meteo API. This eliminates the 2–5 second SSL handshake latency that freezes single-core microcontrollers. *(Fallback: If HTTPS is forced, use `client.setInsecure()`)*.
*   **Targeted Payloads:** Request only the required days and hours via the API URL (e.g., `&forecast_days=7&forecast_hours=12`).
*   **Stream Parsing:** Never store the API response as a `String`. Read directly from `http.getStream()`.
*   **ArduinoJson Filters:** Implement a `JsonDocument` filter to instantly discard unneeded metadata as the stream arrives, parsing only the required keys.

### **2. Memory Management (The C-Struct)**
The parsed JSON data will be immediately transferred into a global C-struct and the JSON document destroyed. This keeps the memory footprint under **400 bytes** (vs. ~20KB for raw JSON) and prevents heap fragmentation.

The struct must include Motorcycle-Specific metrics, particularly **Wind Gusts** and **Visibility**:
```cpp
struct WeatherData {
    // Current (Real-time view)
    float curTemp, curWind, curGusts, curHumidity; 
    int curVisibility;

    // Hourly (Next 12 hours - Commute view)
    float hourlyTemp[12], hourlyWindGusts[12];
    int hourlyRainProb[12];

    // Daily (7 Days - AI Planning view)
    float dailyTempMax[7], dailyTempMin[7];
    float dailyPrecip[7], dailyWindMax[7], dailyGustMax[7];
};
```

### **3. The "AI" Heuristic Scoring Engine**
Instead of forcing the rider to read a 7-day data table, the system will process the `WeatherData` struct to recommend the optimal riding day.
*   **The Logic:** Every day starts with 100 points. Points are deducted for deviations from ideal conditions (e.g., -3 pts per degree away from 20°C, -20 pts per mm of rain, -2 pts per km/h of wind above 20km/h).
*   **Weekend Bias:** Saturday and Sunday receive an automatic +15 point bonus to prioritize weekend route planning over standard commuter days.
*   **Output:** The engine returns the single highest-scoring day to be highlighted on the UI.

### **4. UI/UX Strategy (0.96" Monochrome OLED)**
Due to space and color constraints, the UI will utilize a **3-Screen Carousel** driven by a hardware timer (`Ticker.h`) to ensure animations (e.g., blinking weather icons) run smoothly regardless of background network tasks.

*   **Screen 1: Current Dashboard (The "Go/No-Go" View)**
    *   Large dynamic weather icon.
    *   Current Temp, Sustained Wind, and Max Gusts.
    *   A bold visual indicator (e.g., solid edge line vs. dashed edge line) for immediate "Safe/Unsafe to Ride" recognition.
*   **Screen 2: Commute Sparkline (Next 12 Hours)**
    *   A mini-graph plotting the temperature curve over the next 12 hours.
    *   Vertical bar overlays indicating hours with rain probability.
*   **Screen 3: AI Best Day (Weekend Outlook)**
    *   Highlights the result of the Heuristic Scoring Engine.
    *   Uses high-contrast inverse video (white block, black text) to boldly display the "Best Day" (e.g., `SATURDAY`), alongside its score and primary weather condition.

**Burn-in Mitigation:** The display function must include a pixel-shifting algorithm (moving the entire matrix randomly by 1 pixel every few minutes) or utilize a proximity/light sensor to sleep the display when not actively viewed.
